# 【面试可讲】rerank 扩大候选集改变了工具路由，检索指标变好但答案退化

- 日期：2026-11-01
- 状态：已解决（路由回归）；引用漂移作为已知现象保留

## 现象

给混合检索加 rerank 后，先按“RRF 前 30 名送 rerank，取前 12”实现。68 题对比结果：

- MRR 0.792 → 0.947（17 题排名提升，0 题下降），检索 Recall 仍为 1.000；
- 但路由从 `rag 60 / sql 7 / table 1` 变成 `rag 58 / sql 10 / table 0`；
- `fact_08`、`scan_04`、`scan_05` 三题被 SQL 工具接管，统一回答“未查询到符合条件的记录”；
- 引用命中率从 1.000 降到 0.950。

其中 `scan_04` 原本由扫描件表格工具做确定性核算，答出 68/95/38/201/205；rerank 后被一个 CSV 表格分支抢走，退化为空结果。

## 原因

`answer()` 的工具分流不是只看 top-k 的“名次”，而是看命中列表里是否存在可访问的表格文档：

- `answer_with_tables` 命中 CSV/XLSX；
- `answer_with_scanned_tables` 命中 PDF/PNG 扫描件；
- 两者都依赖 `hits` 的成员集合。

原实现把 RRF 第 13–30 名也送去 rerank，rerank 返回的前 12 名可能包含这些新成员。表格文档一旦被提进上下文，就会先于向量 RAG 触发 SQL/表格分支；而该分支对这类问题并不适用，于是产生“未查询到记录”。检索 Recall 不变，因为 gold 文档本来就在前 12 名内；变的是非 gold 表格文档的成员资格。

## 解决方案

- rerank 只重排**已经召回的 top-k**，不扩大成员：`RERANK_CANDIDATE_K` 默认等于 `TOP_K`；
- 仍保留环境变量 `RAG_RERANK_CANDIDATE_K`，未来召回不足时可显式扩大，但默认不改变工具路由；
- 对比数据保留在 `build/eval/report_rerank12.json`（top-12）与 `report_rerank.json`（top-30）。

## 验证结果

top-12 重排的 68 题对比：

| 指标 | RRF 基线 | rerank top-12 |
|---|---|---|
| MRR | 0.792 | 0.947 |
| 检索 Recall | 1.000 | 1.000 |
| 路由变化 | - | 0 题 |
| 引用命中率 | 1.000 | 0.983 |
| 平均检索延迟 | 0.64 s | 4.26 s |
| 检索费用 | 约 0 元 | 约 0.006 元/题 |

MRR 收益全部保留，路由回归消失。`fact_07` 仍出现引用从 `HR-011` 漂到 `HR-023 第二十条`：内容一致，但 `cites_gold` 按文档 ID 判定为未命中；这是上下文顺序改变后的生成波动，不是检索缺失。

## 结论

- 检索排序指标不能单独决定 rerank 是否上线；工具路由、引用与答案正确性都要一起看。
- 对“按文档类型触发工具”的系统，重排层不应改变候选成员集合，除非同时验证分流逻辑。
- rerank 默认保持关闭，作为可选项保留；开启前应再做一次带 judge 的全量对比。
