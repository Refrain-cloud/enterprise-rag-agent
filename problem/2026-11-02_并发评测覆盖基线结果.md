# 【面试可讲】旧的评测进程没真正停掉，用旧指纹结果覆盖了新基线

- 日期：2026-11-02
- 状态：已解决
- 影响范围：`build/eval/results_m2.jsonl`、`report_m2.*`、默认 `results.jsonl` / `report.json`

## 现象

M2 重构后启动全量评估时，发现一处运行时细节需要修正，于是停掉第一个后台任务并重新启动第二个。第二个任务先完成，日志显示回答指纹 `1187ab40017fd288`、均分 1.9752；随后准备把结果提升为默认基线时，文件内容却变成指纹 `75cef0f837422a9f`、均分 1.9504，且多了 `fact_23`、`ref_08` 两处掉分。

## 原因

- 第一个后台任务收到停止信号后并未立即退出，仍在继续生成；它比第二个任务晚约 2 分钟结束，并按相同参数把 `results_m2.jsonl` / `report_m2.*` 重新写了一遍。
- 两个进程使用**相同的输出文件名**，没有独占写保护；后完成者覆盖先完成者。
- 覆盖后的结果来自改动前的代码，回答指纹与当前代码不一致。若直接提升为默认基线，后续 `--rejudge` 会按指纹校验拒绝复用，基线事实上失效。
- 停止后台任务只保证不再调度新步骤，不能假设已经写出的文件仍属于最后一次逻辑运行；判断基线是否有效必须以**回答指纹**为准。

## 解决方案

- 提升基线前强制核对 `report.fingerprints.answer` 与 `eval.run_eval._answer_fingerprint()` 是否一致；不一致就不得提升。
- 每次全量评估使用独立 `--report-stem` / `--results-name`（本次为 `report_m2_final` / `results_m2_final.jsonl`），确认无并发写入后再复制为默认基线。
- 启动新全量前检查旧进程确实退出（日志最后修改时间不再增长、无对应 python 进程），避免两个重型任务争用同一份索引与输出。

## 验证结果

- 当前代码指纹为 `1187ab40017fd288`，旧结果文件为 `75cef0f837422a9f`，确认被覆盖。
- 用独立文件名重跑全量，结果写入 `report_m2_final.*` / `results_m2_final.jsonl`：121/121 题、121 行指纹全部为 `1187ab40017fd288`、均分 2.0、路由一致率 1.0。
- 指纹校验通过后才覆盖默认基线（`report.*` / `results.jsonl`）；被覆盖的旧指纹结果改名为 `report_m2_stale.*` / `results_m2_stale.jsonl` 留档。
- 默认基线保留历史版本 `report_v5.*` / `results_v5.jsonl`，便于回滚与对比。

## 状态

已解决。工程上把“结果文件是否属于当前代码”从人工记忆改成指纹校验，避免再次把过期结果当成新基线。
