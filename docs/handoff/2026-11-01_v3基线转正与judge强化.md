## 本轮四项工作

### 1. 复合事实与否定式事实恢复（`eval/run_eval.py`）

- **顿号列举 + 共享谓语**：新增 `_enumeration_parts` / `_enumeration_recovery`，支持“定额发票、手撕票一律不予受理”这类结构；共享谓语做同义归一（不予接收/拒收/不得报销/退回 → 不能受理），再按 50% bigram 覆盖率确认。`fact_10` 三轮判分稳定为 `[2,2,2]`，逐事实点状态一致。
- **否定式事实**：`chat_02` 的必答点“不谎称是性能优化”在回答中被写成“明确拒绝以‘优化性能’……”“李维否决该说法”，原规则判 missing。新增 `_negation_recovery`，仅对以“不/未/无/没有/非”开头的事实点启用，要求实词覆盖率 ≥60%，且句子含拒绝类标记。
- **离线审计**：对 68 题所有 missing 事实点重放恢复函数，只有 `chat_02 K1` 翻为 covered；随后用当前代码对全部 68 题事实点重放，状态变化为 0。

### 2. judge 指纹收敛（`eval/run_eval.py`）

- `judge_fingerprint` 从“整个 `run_eval.py` 文件哈希”改为“judge 提示词 + 判定函数源码 + 关键常量”的显式清单（`JUDGE_LOGIC_CONSTANTS` / `JUDGE_LOGIC_FUNCTIONS`）。
- 报告、CLI、稳定性统计的改动不再污染判定凭据；新增否定恢复、JSON 解析修复等真实判定改动仍会改变指纹。
- 常量的序列化对正则、集合做了稳定化处理（`_constant_source`），跨进程指纹一致，已连续验证两次得到同一值。

### 3. 扫描件表格确定性核算（新增 `src/tools/text_table.py`）

- 解析 OCR/PDF 文本中的 Markdown 表格与续页 TSV，按前一页表头补齐；自动识别数值度量列与“X 号工厂/车间/部门”分组列。
- 用 pandas `groupby` 计算分组小计、明细合计，并与表尾“统计/合计”声明值比对；纯聚合问法直接输出带 `[doc_id]` 引用的确定性答案，路由记为 `table`。
- 接入顺序：`answer_with_tables`（CSV/XLSX/SQL）→ `answer_with_scanned_tables`（PDF/PNG/JPG/JPEG）→ 向量 RAG；权限仍由检索层与 `can_access` 双重校验。
- `scan_04` 由“模型心算 97/203、判 1 分”变为直接输出 **68 / 95 / 38 / 201 / 205**，判 **2 分**；扫描件批次平均由 1.875 提升到 2.000。

## 重要决策与细节

- **不改 Gold 换分**：所有修正都在 judge 判定与工具层；题目、`key_facts`、Gold 文档未动。
- **指纹对齐的依据**：68 行判分来自同一次全量运行；`chat_02`、`ref_04` 用当前 judge 实际复判，其余 67 行先用当前代码做确定性事实点重放，确认状态完全一致后再把指纹对齐到当前 judge 代码。没有为对齐指纹重新调用 67×3 次 judge。
- **JSON 修复放在转义之前**：模型偶发把字段值末尾英文引号写成中文 `“`，先按 `“}` / `“]` 结构位置修回，再尝试 `_escape_inner_quotes`；顺序反过来会误转义后续结构引号。
- **扫描件表格只处理可解析的分组表**：单一数值列 + 分组列的聚合问法走确定性路径；多表关联、跨表合计仍回退到 SQL/向量路径。
- **稳定性报告口径**：`report_stability.{json,md}` 仍是 60 题修复前的历史报告（fact_10 当时 `[1,2,1]`）；本轮 `report_stability_fact10` 记录修复后 `[2,2,2]`。权威 v3 的三轮一致率以报告中的 `judge_score_agreement` 为准。
- **成本**：全量 68 题 = 68 次生成 + 204 次 judge；本轮额外约 20 次 judge 诊断/局部复判（`chat_02`、`ref_04` 及 JSON 解析定位）。未接入 token 计量，无法给出精确费用。

## 已知问题

1. **judge 对“数值算错但原文无冲突”仍是盲区**：`wrong` 判定依赖与原文直接冲突，`scan_04` 这类算术错误本次靠工具路径规避，未改 judge 语义。
2. **扫描件多表聚合未覆盖**：当前只支持单表分组求和；跨表关联、跨页表头变化仍需 SQL 路径。
3. **历史稳定性报告与当前 judge 不同版**：`report_stability.json` 为 60 题旧版；如需要 68 题逐事实点稳定性，需再跑 68×3 次 judge（约 204 次调用），执行前先确认预算。
4. **无 token/费用统计**：只有调用次数与延迟，没有生成/judge 的 token 用量。
5. `problem/` 与仓库根目录存在两份与本轮无关的 `工作流程记录_*.md`，未纳入提交。

## 面试可讲的问题

- **模型会把表格加数全部抄对却算错总和**：扫描件点位表 10 个加数正确，模型仍得出 97（实际 95）、合计 203（实际 201）；改为表格结构化 + pandas 确定性求和后，答案与表尾 205 的不一致也能如实指出。
- **“分数稳定”不等于“判分稳定”**：整题得分一致率很高，但拆到事实点仍会暴露 judge 的漏判；否定式事实被改写为“拒绝/否决”时，需要专门的语义恢复规则，而不是放宽逐字匹配。
- **评估链路自身的健壮性**：judge 模型偶发输出未闭合 JSON，解析器的修复顺序（先修结构引号、再转义内部引号）决定了能否恢复；这类问题会以 `score=None` 的形式污染稳定性统计，必须单独定位。
