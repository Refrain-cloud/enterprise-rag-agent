## 本轮三项工作

### 1. token / 费用 / 延迟采集（`src/llm.py`）

- 新增统一封装：`chat_completion(kind, ...)`、`embed(kind, ...)`，自动读取响应 `usage` 并记录调用类型、模型、prompt/completion token、耗时。
- 调用类型：`generate`、`sql_generate`、`sql_restate`、`judge`、`contradiction`、`embedding`、`rerank`。
- 价格表为人民币元/百万 token：qwen-plus 输入 0.8、输出 2.0；text-embedding-v3 输入 0.5；gte-rerank-v2 输入 0.8。可用 `RAG_PRICE_PER_MILLION` 传 JSON 覆盖。
- 每题记录 `generation_usage`、`judge_usage`、`retrieval_calls`、`retrieval_latency_s`；报告新增 `cost` 字段，Markdown 增加生成/judge token、费用与延迟。
- 稳定性与复判报告单独统计 judge 费用，并把复判时重新检索的 embedding 费用单列，避免“judge 单价”被稀释。

### 2. 可选 rerank 与对比（`src/retrieval/rerank.py`、`src/retrieval/search.py`）

- `RAG_RERANK=1` 开启，模型 `gte-rerank-v2`；默认关闭。
- 只重排已召回的 top-k（`RERANK_CANDIDATE_K` 默认等于 `TOP_K=12`），不扩大上下文成员，避免改变工具路由。
- 接口失败自动回退 RRF 顺序并只告警一次，不中断评估。
- 新增 `eval/compare_reports.py`，对比两份报告的 Recall/覆盖率/MRR/引用/延迟/费用与逐题排名变化。

## 重要决策与细节

- **rerank 不扩成员**：先做的“30 候选送 rerank、取 12”导致 3 题从 rag/table 改路由到 sql 并答成“未查询到记录”，MRR 仍为 0.947。改为只重排 top-12 后 MRR 收益完全保留、路由零变化；因此 `RERANK_CANDIDATE_K` 默认等于 `TOP_K`。
- **rerank 默认关闭**：排序收益不等于答案收益；rerank 对比未判分，且检索延迟 +3 秒。保留开关与对比报告，等带判分验证后再决定是否转正。
- **计费口径**：费用是估算值，按公开价目与响应 usage 计算；qwen-plus 可能分档计价，不能当作账单金额。
- **稳定性报告重写**：发现“judge 费用”误把复判 embedding 算进去后，修正代码并直接重写已生成报告的成本字段，没有额外调用 judge。
- **基线重跑原因**：改了 `RERANK_CANDIDATE_K` 默认值，`src/config.py` 进入回答指纹，旧结果失效，因此用最终代码重跑了一次 68 题全量；指标与上一轮一致。
- **本轮用量**：最终基线 1.44 元 + rerank 两版 1.57 元 + 稳定性 1.16 元 + 冒烟/诊断约 0.1 元，合计约 **5.7 元**；judge 调用 612 次（两次全量基线各 204 + 稳定性 204）。

## 已知问题

1. **rerank 未带判分验证**：top-12 对比只证明 MRR/路由，不证明答案分数与忠实率；`fact_07` 引用漂移也说明上下文顺序会影响生成。
2. **rerank 延迟较高**：每次检索约 +3.3 s，主要来自两次 rerank 调用（`hits` 与 `best_overall` 各一次）；如要上线，应合并或跳过仅用于权限判断的 top-1 检索。
3. **judge 自拆点稳定性口径偏保守**：0.737 把同义改写和 judge 漏项都计为不一致，无法区分“答案没写”和“judge 没列”；有必答点的 1.000 更能代表核心事实稳定性。
4. **检索延迟波动**：同一配置两轮分别为 0.64 s 与 1.30 s/题，embedding 网络耗时占比高；跨批次比较需同批次运行或多次取中位数。
5. **价格与账单可能有差异**：未接入账单 API，费用只用于迭代预算。
6. 根目录两份 `工作流程记录_*.md` 仍与本项目无关，未纳入提交。

## 面试可讲的问题

- **重排扩大候选集，检索指标变好但答案退化**：30 候选 rerank 让 MRR 从 0.792 升到 0.947，却把表格文档挤进上下文，触发 SQL 分支，3 题答成“未查询到记录”；限制为只重排 top-12 后收益保留、路由恢复。见 `problem/2026-11-01_rerank扩候选改变工具路由.md`。
- **分数稳定 ≠ 判分稳定**：68 题整题分数 100% 一致，但拆到 judge 自拆点仍有 5 个点不一致；根因是模型每次改写事实点措辞，而不是答案变化。
- **成本必须先量化**：单次全量 68 题约 1.44 元，其中 judge 占 80%（1.16 元）；扩到 120 题并跑三轮，预算应按 judge 次数线性估算。

## 下一步任务（按优先级）

1. **rerank 是否转正**：跑一次 68×3 带判分的 rerank-on 基线，比较平均分、忠实率、引用命中与延迟；通过后再改默认值并重跑权威基线。
2. **120 题扩展**：按类别分层，Gold 回原文核对；用当前 1.44 元/68 题的口径预估预算。
3. **judge 数值错误识别**：区分“没写”和“写错”，覆盖非表格路径的算术类回答。
4. **自拆点稳定性归因**：把“同义改写”和“judge 漏项”分开统计，避免 0.737 被误读为回答不稳定。
5. **LangGraph 编排与 FastAPI/Web Demo**：在确定性基线上接入角色切换、引用展示与成本面板。
