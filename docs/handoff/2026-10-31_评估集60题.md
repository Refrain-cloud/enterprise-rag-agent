## 4 个 1 分及原因

- `agg_02`：SQL 只取 BG-001 的“现场差旅增加”，未合并 XS-001 说明中的“恒远精工、华中二期现场周期延长”。
- `fact_10`：未明确“税号错误的发票不予受理”，只写了抬头/税号必须正确。
- `multi_04`：`CV-003`（客户不愿承担模块费用、我方拟承担一半）未进 top-8。
- `multi_05`：`CV-008`（增购 EN-1、30 万、明年 Q1）未进 top-8。

以上均为真实缺口，未通过修改 gold 消除。

## 重要决策与原因

- **老题也补 `key_facts`**：原计划“老题逐步回填”，但复判发现无 `key_facts` 时 LLM 拆点粒度会漂移（`fact_03`/`multi_03` 2↔1）。最终 52 道非拒答题全部显式声明必答点，评分才稳定。
- **必答点只覆盖问题所问**：如 `fact_06` 不再要求“工期 5–8 人日”，`agg_03` 不再要求“编制/在岗”，`perm_03` 不再要求“质保期”。这是明确评分范围，不是放宽 gold。
- **找回只做兜底，不替代 judge**：确定性找回只处理 key_facts 的 missing/wrong，且要求数字/覆盖率达到阈值；`fact_10`、`multi_04` K4、`multi_05` K3/K4 都没有被误放。
- **聚合题按需放宽候选**：不是全局提高 `TOP_K`，只在“聚合题 + top-K 无表格”时放宽到 10，避免正常题混入无关表格。
- **局部结果不自动进基线**：`--ids` 只写 `report_partial`；并入基线必须 `--merge-partial --ids ...`，合并后标记混合指纹并在报告中警告。
- **用抽样决定是否全量**：检索/路由漂移 → 必须全量生成；只有措辞变化且判定稳定 → 全量复判即可。

## 已知问题与风险

1. `multi_04`/`multi_05` 是检索召回缺口；下一步应先看 `CV-003`/`CV-008` 的 chunk 与排序，而不是改 judge。
2. `agg_02` 是多表合并缺口：同一问题的事实分散在 BG-001 汇总和 XS-001 说明，SQL 生成只查了一张表。
3. 无数字事实的整篇匹配仍是启发式；高度改写可能误判或漏判。
4. 评估仍未记录 token 用量与费用。
5. `questions.v1.jsonl` 保留为历史文件，但 `QUESTIONS_PATH` 已指向 `questions.v2.jsonl`。
6. **产物口径**：`results.jsonl` 的 `judge` 字段已按 id 从 `results_rejudge.jsonl` 合并，与最终报告一致（60 题，4×1 / 56×2），合并前备份为 `results.pre_judge_merge.jsonl`；结论仍以 `report_rejudge.md` 为准。注意：最后一次全量生成早于最终 SQL/检索改动，当前基线是“旧回答 + 新 judge + `agg_06`/`agg_07` 补跑”，不是当前代码全量重生成的结果；已决定暂不重跑，需要纯净基线时再跑全量生成。当前基线产生于加入指纹之前，缺少 `answer_fingerprint`，下一次 `--rejudge` 会被拦截，需全量重生成或显式 `--allow-stale`。
