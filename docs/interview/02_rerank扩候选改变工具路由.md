# 故事 2：rerank 扩大候选集，检索指标变好但答案退化

**一句话版本**：MRR 从 0.792 提到 0.947，引用和答案却掉了——因为重排把新的表格文档带进上下文，改变了工具路由。

## 适用问题

- 你们怎么做检索优化？怎么决定 rerank 要不要上？
- 指标变好但线上效果变差，遇到过吗？

## 现象

给混合检索加 rerank，第一版实现是“RRF 前 30 名送 rerank，取前 12”。68 题对比：

- MRR 0.792 → 0.947，17 题排名提升、0 题下降；Recall 仍是 1.000。
- 但路由从 `rag 60 / sql 7 / table 1` 变成 `rag 58 / sql 10 / table 0`。
- `fact_08`、`scan_04`、`scan_05` 被 SQL 工具接管，统一回答“未查询到符合条件的记录”。
- 引用命中率 1.000 → 0.950。
- `scan_04` 原本由扫描件表格工具算出 68/95/38/201/205，rerank 后被一个 CSV 分支抢走，结果为空。

## 排查

工具分流不是只看“第几名”，而是看命中集合里有没有可访问的表格文档：

- `answer_with_tables` 命中 CSV/XLSX；
- `answer_with_scanned_tables` 命中 PDF/PNG 扫描件；
- 两者都依赖 `hits` 的**成员集合**。

第一版把第 13–30 名也送去 rerank，rerank 返回的 top-12 里就可能包含原本不在上下文里的表格文档。表格文档一进来，就先于向量 RAG 触发 SQL/表格分支。Recall 没变，是因为 gold 文档本来就在前 12；变的是**非 gold 文档的成员资格**。

## 决策

- rerank 只重排**已召回的 top-k**，不扩大成员：`RERANK_CANDIDATE_K` 默认等于 `TOP_K`。
- 保留 `RAG_RERANK_CANDIDATE_K` 环境变量，未来召回不足时可以显式扩大，但默认不改变路由。
- 评估时同时看检索、路由、引用和答案四个层面，不只看 MRR。

## 验证

top-12 重排的 68 题对比：

| 指标 | RRF 基线 | rerank top-12 |
|---|---|---|
| MRR | 0.792 | 0.947 |
| 检索 Recall | 1.000 | 1.000 |
| 路由变化 | — | 0 题 |
| 引用命中率 | 1.000 | 0.983 |
| 平均检索延迟 | 0.64 s | 4.26 s |
| 检索费用 | 约 0 元 | 约 0.006 元/题 |

带 judge 的 68 题生成 + 204 次判分：MRR 0.947、引用 1.000、忠实 1.000、拒答 1.000、权限合规 1.000、平均分 1.985。唯一掉分的 `perm_01` 追查是生成不可复现的字段合并，rerank on/off 各 11 次都约 9% 出现，不是 rerank 回归。

延迟 4.281 s/题（其中 rerank 3.225 s），生成费用 1.8505 元/68 题。**结论：rerank 保持默认关闭**——MRR 有收益，但没有答案质量收益，延迟和费用明显增加。

## 取舍与边界

- 对“按文档类型触发工具”的系统，重排层不应改变候选成员集合，除非同时验证分流逻辑。
- 检索指标是局部指标，答案质量是全局结果；两者冲突时以端到端评估为准。
- 仍有一个引用漂移：`fact_07` 从 `HR-011` 漂到 `HR-023`，内容一致但按文档 ID 判未命中，属于上下文顺序变化后的生成波动。

## 常见追问

**那为什么还保留 rerank？**
作为可选项保留。它确实提升排序，适合未来召回不足或上下文预算更宽松的场景；当前默认关闭是成本/收益权衡，不是实现失败。

**怎么发现这个问题的？**
不是看总分发现的，是对比路由分布和逐题 diff。`scan_04` 从确定性表格结果变成“未查询到记录”，这种退化在 MRR 上看不出来。
